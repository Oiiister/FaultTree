# 项目问题清单

> 核心功能：**工业文本 + 用户给定顶事件 → 系统自动生成故障树**
> 分析范围：知识抽取管线 → 知识图谱存储 → 故障树生成/校验 → 前端交互，全链路。

---

## 一、真实架构（与分析前假设的差异）

项目里实际存在 **三套故障树前端**，只有一套是端到端打通的：

| 前端 | 技术栈 | 与后端的关系 |
| --- | --- | --- |
| React `RetrievalTesting.tsx` → `POST /query/fault-tree-json` | React（检索页） | ✅ 唯一真正打通的「文本 → 三元组 → 故障树」链路，但藏在"检索"标签页 |
| `fault-tree-app`（"故障树"标签页） | Vue 3（被 React 外壳 `mountFaultTreeApp()` 挂载） | ⚠️ "生成"调用后端后**丢弃结果**，树是纯前端从上传 JSON 拼的 |
| 仓库根目录 `fault-tree-ui` | Vue 3（遗留） | ❌ `baseURL='/api/v1'`，后端无此前缀，全部 404 |

**关键结论**：`src/fault-tree-app/` 不是 React，而是被 React 外壳挂载进来的 Vue 3 应用（`lightrag_webui/src/features/FaultTreeViewer.tsx:15`）。

---

## 二、问题清单（按严重程度排序）

### 🔴 P0 —— 直接决定故障树对错的结构性缺陷

#### P0-1 因果方向在存储层被毁掉，靠启发式猜回来
- **问题**：故障树的两大语义之一「谁是因、谁是果」没有被当作一等数据保存。
  - 抽取时方向正确（因→果），但合并时 `sorted_edge_key = tuple(sorted(edge_key))` 把边**按字母序重排**，方向丢失（`lightrag/operate.py:2562`）。
  - 存储后端 `nx.Graph()` 是无向图（`lightrag/kg/networkx_impl.py:68`），`get_knowledge_graph` 又把端点**字典序重排**（`lightrag/kg/networkx_impl.py:484-485`）。
  - 生成树时 `_orient_fault_tree_edge` 靠「BFS 距离 + 事件类型优先级」重新猜方向；距离相等或类型相同的边 fall through 到任意顺序（`lightrag/api/routers/query_routes.py:400-429`）。
- **影响**：多层故障树中，同级兄弟节点（距顶事件等距）之间的因果方向几乎必然随机，父/子关系会错。
- **建议**：把因果方向作为边的一等属性持久化（不参与字母序重排），或改为有向图存储。

#### P0-2 AND/OR 门不是一等字段，AND 靠「合成节点」硬凑
- **问题**：
  - `resultsIn` / `jointly_resultsIn` 只作为自由文本塞在边的 `keywords` 字符串里，合并时被**排序、逗号拼接**（`lightrag/operate.py:2098-2115`），无结构化字段、无校验。
  - 生成时 `_extract_fault_tree_relation` 扫不到这两个 token 就**静默丢弃整条边**（`lightrag/api/routers/query_routes.py:519-521`）。
  - AND 逻辑靠 prompt 让 LLM 造「A+B组合」中间节点实现（`lightrag/prompt.py:91-98`），完全依赖模型自觉，无后校验。
- **影响**：AND/OR 门类型丢失或错误，边被静默丢弃，树结构不完整。
- **建议**：把门类型（`resultsIn`=OR / `jointly_resultsIn`=AND）提取为边的结构化字段，并在解析/合并阶段校验。

#### P0-3 「用户给定顶事件」这一核心需求没有落地
- **问题**：两个流程里顶事件都是**推断**出来的，没有可编辑的顶事件输入框驱动生成：
  - Flow B 前端按优先级猜：第一个 `object_type==='TopEvent'` → 否则文件名 → 否则硬编码"顶事件"（`lightrag_webui/src/fault-tree-app/src/components/NaiveTailwind.vue:2270-2277`）。
  - Flow A 把整段检索词当顶事件传给后端匹配。
- **影响**：与需求「用户给出顶事件」不符，用户无法精确指定要生成的顶事件。
- **建议**：把顶事件做成显式一等输入，让 `/query/fault-tree-json` 真正接收 `top_event` 参数并据此构图。

### 🟠 P1 —— 抽取质量与鲁棒性

#### P1-1 没有实体消解/共指消解
- 实体按精确字符串合并（`lightrag/operate.py:2556-2558`），"轴承过热"和"轴承温度过高"变成两个节点，代词/"该故障"直接丢失。
- **影响**：同一故障被拆散成多个节点，树被重复/割裂。
- **建议**：至少做同名归一 + 简单共指（LLM 或嵌入相似度）。

#### P1-2 分块割断长因果链
- `chunk_token_size=1200`（`lightrag/lightrag.py:310-316`），跨块因果链只能靠"名字完全重复"连上，prompt 要求的"保留完整中间链条"静默失败。
- **建议**：跨块做实体对齐，或对长链做二阶段聚合抽取。

#### P1-3 关系幻觉无验证
- prompt 要求"只抽取明确陈述的因果"（`lightrag/prompt.py:44,75`），但没有对源文本的回验；LLM 编造/过度泛化的关系直接进图；`resultsIn` vs `jointly_resultsIn` 的区分纯靠 LLM 判断。
- **建议**：增加对源文本的 grounding 校验（关系是否能在原文中找到支撑句）。

#### P1-4 静默截断
- 子图 `max_depth=20` + `max_nodes=1000`，且 `is_truncated` 标志**从不被检查**（`lightrag/api/routers/query_routes.py:500-504`）。
- **影响**：大树被悄悄砍断，用户不知道结果不完整。
- **建议**：把 `is_truncated` 暴露到响应里。

#### P1-5 静默降级
- 图谱没命中时 `POST /query/fault-tree-json` **无提示地**改用 LLM 直接生成（`lightrag/api/routers/query_routes.py:998-1010`）。
- **影响**：客户端不知道结果是否有图谱依据还是纯 LLM 编的。
- **建议**：响应里加 `source: "graph" | "llm"` 标志。

---

### 🟡 P2 —— 一致性与工程债

#### P2-1 校验器与生成器脱节
- `POST /fault-tree/validate` 的结构化检查很扎实（环检测 Kahn、层级/孤点/门度检查，`lightrag/api/routers/fault_tree_validation_routes.py:577-964`）。
- 但它的输入 schema（`top/middle/basic/gate` 节点+边）和生成器输出（`resultsIn` 三元组）**不是同一结构**，中间无转换层，得靠客户端自己拼。
- KG 一致性检查默认关闭（`fault_tree_validation_routes.py:58-61`），在无向图后端上判断"方向冲突"不生效（`fault_tree_validation_routes.py:399-422`）。
- **建议**：加一个「三元组 → 校验图」的转换层；方向类校验在有向存储落地后再启用。

#### P2-2 置信度硬编码
- 每条三元组置信度硬编码 `0.9`（`lightrag/api/routers/query_routes.py:556`），不是从抽取可靠性来的，前端展示无意义。
- **建议**：从抽取可靠度/验证结果推导置信度。

#### P2-3 大量死代码
- `fault-tree-app` 的 API 层声明了 7 个后端不存在的端点：`/fault-tree/upload_knowledge`、`/knowledge/extract`、`/ai/chat`、`/fault-tree/optimize`、`/fault-tree/export`、`/fault-tree/generate_and_download`、`/fault-tree/download/:filename`。
- 外加整套遗留 `fault-tree-ui`（`baseURL='/api/v1'`）。
- **影响**：误导后续开发，增加维护成本。
- **建议**：收敛前端，砍掉死端点和遗留应用。

---

## 三、做得还不错的点

- 抽取 prompt 的 FTA 概念（顶/中间/底事件、AND/OR、`resultsIn`/`jointly_resultsIn`）设计清晰，贴合故障树语义（`lightrag/prompt.py:11-79`）。
- 结构化校验器（环检测、层级、孤点、门度）有真实算法含量，不是走形式。
- Flow A（检索页生成三元组 JSON）能端到端跑通，底层 RAG/图谱基建（LightRAG 本体）成熟。

---

## 四、改进优先级建议

1. **治本**：把 `resultsIn`/`jointly_resultsIn` 变成边的结构化字段，并保留因果方向（别在 merge 时 `sorted(edge_key)`）—— 解决 P0-1、P0-2。
2. **落地核心需求**：把「顶事件」做成显式一等输入，`/query/fault-tree-json` 接收 `top_event` 参数 —— 解决 P0-3。
3. **前端收敛**：三套前端留一套（建议 React 外壳 + 内嵌 Vue 编辑器为主），砍掉死端点与遗留 `fault-tree-ui` —— 解决 P2-3。
4. **提升质量**：实体消解 + 共指（P1-1）、分块对齐（P1-2）、暴露 `is_truncated`/`from_graph` 标志（P1-4、P1-5）。
