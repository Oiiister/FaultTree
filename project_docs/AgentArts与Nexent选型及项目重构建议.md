# AgentArts 与 Nexent 选型及项目重构建议

## 一、结论

结合本项目现有代码基础、技术路线和需要解决的问题，建议：

> **当前优先选择 Nexent 作为 Agent 协作和重构平台，保留 LightRAG 作为检索与知识处理核心；不要直接替换现有 LightRAG。**

如果未来项目需要部署到华为云企业生产环境，再考虑使用 AgentArts 作为 Agent 托管、治理和观测平台。

参考资料：

- [项目成果总结](../项目成果总结(1).pdf)
- [项目概要介绍](../项目概要介绍(1).pdf)
- [AgentArts 产品介绍](https://support.huaweicloud.com/productdesc-agentarts/agentarts_03_0002.html)
- [Nexent 项目概览](https://modelengine-group.github.io/nexent/zh/getting-started/overview.html)

## 二、项目现状和主要不足

项目目前已经具备以下基础能力：

- 基于 LightRAG 的文档解析、向量检索和图谱检索；
- 故障事件三元组抽取；
- 故障树生成和逻辑校验；
- React 前端故障树编辑器；
- FastAPI 后端接口；
- Docker 化部署基础；
- 已经跑通“文档入库 → 检索 → 三元组 → 故障树 → 编辑 → 校验”的闭环。

当前主要问题包括：

1. 长文本和多文档抽取准确率下降；
2. 抽取、校验和修复主要依赖人工修改提示词；
3. 三元组模型和故障树的节点-逻辑门模型没有统一；
4. 节点置信度缺乏可解释、可量化的计算方式；
5. 生成结果需要手动下载和上传，端到端流程不完整；
6. AI 专家辅助功能尚未真正实现；
7. 缺少系统化评测集和持续优化机制；
8. 图数据库、向量数据库、关系数据库之间的职责还不够清晰。

## 三、为什么优先选择 Nexent

### 1. 与现有技术栈匹配度更高

项目不是从零开发，而是已经拥有 LightRAG、FastAPI、React 和故障树领域逻辑。Nexent 更适合在保留现有代码的基础上，增加多 Agent 编排、工具调用、知识库、记忆和评估能力。

AgentArts 也支持 LangChain、LangGraph 和自研框架，但它更偏向企业级托管和治理平台。若直接使用，通常需要更多平台接入和部署适配工作。

### 2. 更适合实现多 Agent 抽取和校验

Nexent 提供 Agent、A2A 协作、Skill、MCP 工具、知识库和评估能力，适合把当前的“提示词反复试错”升级为可执行的抽取工作流。

建议把任务拆成：

- 文档分析 Agent；
- 故障事件抽取 Agent；
- 因果关系抽取 Agent；
- 一致性校验 Agent；
- 局部修复 Agent；
- 故障树生成 Agent；
- AI 专家辅助 Agent；
- 评估与迭代 Agent。

### 3. 更适合本地和私有化部署

Nexent 官方提供 Docker Compose 和 Kubernetes 部署方式，采用 MIT 许可证，适合课程项目、竞赛项目、毕业设计以及后续自主维护。

其官方架构使用 PostgreSQL、Elasticsearch、Redis 和 MinIO 分别承担业务数据、检索索引、缓存/任务队列和对象存储职责，与本项目未来引入数据库的计划较为契合。

### 4. 可补足当前缺少的工程能力

Nexent 可以帮助项目增加：

- 多 Agent 工作流；
- A2A Agent 协作；
- MCP 工具接入；
- Skill 按需调用；
- 分层记忆；
- 知识级溯源；
- Agent 版本管理；
- 评测集和评估器；
- 异步任务和流式结果；
- Docker/Kubernetes 部署能力。

## 四、AgentArts 与 Nexent 的对比

| 需求                   | Nexent                                 | AgentArts                                       |
| ---------------------- | -------------------------------------- | ----------------------------------------------- |
| 保留现有 LightRAG 后端 | 更适合，支持源码级二次开发和自部署     | 可以通过运行时托管或 API 接入，但平台化改造更多 |
| 多 Agent 抽取和校验    | 支持 A2A 协作、Agent、Skill、MCP       | 支持单 Agent、工作流和多 Agent                  |
| 自定义故障树逻辑       | 可写自定义 Skill、工具和业务代码       | 可以实现，但通常依赖平台运行时和工具接入        |
| 文档知识库与溯源       | 支持多种文档、知识库和知识级溯源       | 支持企业知识库和 RAG                            |
| 自动评估               | 支持智能体评估、评测集和评估器         | 提供全链路观测与自动评估                        |
| 本地/私有化部署        | Docker Compose、Kubernetes，MIT 许可证 | 更偏向华为云企业平台                            |
| 改造成本               | 较低                                   | 中高                                            |
| 企业级治理、审计、弹性 | 需要自行建设                           | AgentArts 更强                                  |

可以简单理解为：

> Nexent 更适合“重构和增强现有研究型系统”；AgentArts 更适合“将成熟系统托管到华为云企业生产环境”。

## 五、推荐的总体架构

不建议用 Nexent 完全替换现有 LightRAG，而建议采用“Agent 编排层 + 领域服务层”的架构：

```text
Nexent
  ├── 抽取 Agent
  ├── 校验 Agent
  ├── 故障树推理 Agent
  ├── AI 专家辅助 Agent
  └── 评估与迭代 Agent
          │
          ├── MCP / API
          │
          └── 现有 LightRAG + 故障树服务
                    ├── 文档处理
                    ├── 向量检索
                    ├── 知识图谱
                    ├── 故障树生成
                    └── 规则校验
```

Nexent 负责 Agent 的编排、记忆、工具调用、评估和交互；LightRAG 继续负责文档处理和检索；现有故障树模块继续负责领域逻辑。

这种方案可以避免一次性推倒重来。

## 六、抽取层重构方案

### 1. 从单次抽取升级为多 Agent 流水线

当前做法本质上是：

```text
提示词设计 → LLM 抽取 → 人工看结果 → 修改提示词 → 重试
```

建议升级为：

```text
文档分析 → 事件抽取 → 关系抽取 → 一致性校验 → 评分 → 局部修复/人工审核
```

### 2. 文档分析 Agent

负责：

- 判断文档类型；
- 识别章节、标题、表格和步骤；
- 按设备、部件、故障现象、维修步骤进行语义切分；
- 生成文档级元数据。

长文档不应只按固定 token 数切分，而应采用“章节 + 语义 + 事件链”的混合切分方式。

### 3. 故障事件抽取 Agent

每个事件必须包含结构化信息和原文证据：

```json
{
  "event_id": "E001",
  "name": "液压泵压力不足",
  "event_type": "intermediate",
  "description": "...",
  "conditions": [],
  "evidence": [
    {
      "document_id": "manual_01",
      "chunk_id": "chunk_008",
      "quote": "..."
    }
  ]
}
```

抽取结果不能只有节点名称，还必须保存支持该节点的原文片段。

### 4. 因果关系抽取 Agent

关系建议使用有限集合，避免前后端各自接受任意关系：

- `resultsIn`：单一因果；
- `jointly_resultsIn`：多个原因共同导致结果；
- `partOf`：组成关系；
- `conditionOf`：条件关系；
- `contradicts`：冲突关系；
- `similarTo`：同义或近似关系。

故障树生成主要使用因果关系，其他关系用于知识管理和辅助检索。

示例：

```json
{
  "source": "液压泵滤芯堵塞",
  "relation": "resultsIn",
  "target": "液压泵压力不足",
  "evidence": "...",
  "confidence": 0.86
}
```

### 5. 一致性校验 Agent

重点检查：

- 节点是否有原文证据；
- 关系方向是否反了；
- 顶事件、中间事件、基本事件层级是否合理；
- 是否存在自环；
- 是否存在同义节点重复；
- 是否混淆“故障现象”和“故障原因”；
- 是否将维修措施误识别成原因。

### 6. 局部修复 Agent

根据校验结果只修复有问题的字段，而不是重新生成整个图谱。这样可以提高稳定性，并降低 LLM 调用成本。

## 七、双模型抽取、校验和评分机制

你们之前设想的“两模型互相抽取、评分、循环”是可行的，但不建议设计成无限循环，而应采用有限状态机：

```text
抽取
  ↓
规则检查
  ↓
独立校验
  ↓
评分
  ├── 评分 ≥ 阈值：入库
  ├── 中间分数：局部修复
  └── 评分过低：转人工审核
```

可采用如下示例评分公式：

```text
总分 = 0.30 × 结构完整性
     + 0.25 × 证据覆盖率
     + 0.20 × 关系方向正确率
     + 0.15 × 层级一致性
     + 0.10 × 与已有图谱一致性
```

模型输出的 `confidence` 不应直接视为真实准确率。建议根据以下可解释特征计算置信度：

- 是否有证据；
- 证据是否直接支持结论；
- 是否通过规则校验；
- 是否有多个文档交叉支持；
- 是否与已有知识冲突；
- 是否通过第二个模型复核。

## 八、统一三元组和故障树数据模型

你们当前的问题不是“三元组模型错误”，而是缺少统一领域模型。建议保留三元组作为知识图谱层，并增加统一的领域中间模型。

### 1. 建议的统一模型

```text
FaultEvent
  ├── id
  ├── name
  ├── type: top/intermediate/basic
  ├── description
  ├── evidence[]
  ├── confidence
  └── source_documents[]

FaultRelation
  ├── source_event_id
  ├── target_event_id
  ├── relation_type
  ├── gate_type
  ├── evidence[]
  └── confidence

FaultTree
  ├── root_event_id
  ├── nodes[]
  ├── gates[]
  └── validation_result
```

三元组表达事实：

```text
实体1 — 关系 — 实体2
```

故障树表达结构和逻辑：

```text
FaultEvent + FaultRelation
              ↓
        FaultTree Projection
              ↓
       节点 + AND/OR 门
```

### 2. 三元组到故障树的投影

单一因果：

```text
滤芯堵塞
  resultsIn
液压泵压力不足
```

可以投影为：

```text
液压泵压力不足
        OR
   滤芯堵塞
```

多个原因共同导致结果：

```text
油温过高 jointly_resultsIn 液压泵压力不足
油液黏度异常 jointly_resultsIn 液压泵压力不足
```

可以投影为：

```text
油温过高 ─┐
          AND → 液压泵压力不足
油液黏度异常 ─┘
```

核心原则是：

> 三元组保存事实和证据，故障树保存结构和逻辑门，两者是“事实层 → 推理结构层”的关系，而不是两套互相独立的数据。

### 3. 建议的统一 API

```text
POST /events/extract
POST /relations/extract
POST /graph/upsert
POST /fault-trees/project
POST /fault-trees/validate
POST /fault-trees/revise
GET  /evidence/{event_id}
```

前端不再通过下载 JSON 再上传，而采用：

```text
生成任务 → 后端保存 draft → 前端获取 draft_id → 编辑 → 保存修订 → 校验
```

这样可以解决生成结果丢失、前后端关系契约不一致以及手动串接等问题。

## 九、数据库和存储建议

可以采用分层存储：

- PostgreSQL：故障树版本、任务、用户、审核记录；
- Neo4j 或 Memgraph：故障事件和因果关系；
- Elasticsearch 或 OpenSearch：全文和混合检索；
- Qdrant 或 Milvus：向量检索；
- MinIO：原始文档和生成文件；
- Redis：任务队列、缓存和流式状态。

为了降低改造成本，可以先保留 LightRAG 当前存储，将统一模型写入 PostgreSQL，随后再逐步把图关系迁移到 Neo4j 或 Memgraph。

## 十、AI 专家辅助功能设计

“AI 专家辅助”不应只是一个普通问答框，而应设计成带证据、带操作建议、带人工确认的故障树 Copilot。

### 1. 故障树解释

用户点击某个节点时，AI 返回：

- 节点含义；
- 可能原因；
- 支持该节点的原文；
- 使用了哪些文档；
- 当前置信度；
- 与哪些节点存在冲突。

### 2. 结果审核

AI 自动列出：

- 低置信度节点；
- 没有证据的节点；
- 疑似重复节点；
- 关系方向可疑的边；
- 可能缺失的中间事件；
- AND/OR 门不确定的位置。

### 3. 自然语言修改

例如专家输入：

> 液压泵压力不足通常还可能由吸油管漏气导致，请补充这个原因。

系统生成一个待审核变更：

```json
{
  "operation": "add_relation",
  "source": "吸油管漏气",
  "relation": "resultsIn",
  "target": "液压泵压力不足",
  "evidence_required": true,
  "status": "pending_review"
}
```

不要让 Agent 直接把修改写入正式知识库，而应先进入待审核状态。

### 4. 冲突处理

如果不同文档给出的原因不一致，AI 应展示：

- 文档 A 的结论；
- 文档 B 的结论；
- 两者的适用工况；
- 建议新增条件节点，还是由专家选择其一。

### 5. 审核闭环

```text
AI 建议 → 专家接受/修改/拒绝 → 保存审核记录 → 更新知识库 → 加入评测集
```

人工审核数据可以反过来用于优化提示词、Agent 和评测集。

## 十一、AgentArts 什么时候更合适

虽然当前推荐 Nexent，但 AgentArts 在以下场景更有优势：

1. 决定将系统部署到华为云，而不是本地或自建服务器；
2. 项目需要面向企业客户长期运行；
3. 需要 IAM、OAuth、API Key、多租户和权限隔离；
4. 需要较完整的调用链追踪和生产监控；
5. 需要高并发、弹性扩缩容和托管运行；
6. 团队不希望自行维护 Agent runtime、沙箱和基础设施；
7. 未来需要接入华为云模型、数据服务和企业系统。

此时可以保留现有故障树服务，把它包装成 AgentArts 可以调用的 API 或工具：

```text
AgentArts
  ├── 文档问答 Agent
  ├── 故障抽取 Agent
  ├── 专家审核 Agent
  └── 故障树分析 Agent
          │
          └── 调用现有 LightRAG/FastAPI 服务
```

AgentArts 更像部署和治理层，而不是替代故障树核心算法。

## 十二、推荐的实际重构路线

### 第一阶段：统一数据模型

优先修改现有项目，不急着接入平台：

1. 定义 `FaultEvent`、`FaultRelation`、`FaultTree`；
2. 明确关系枚举；
3. 增加证据字段；
4. 增加版本和审核状态；
5. 实现“三元组 → 故障树”的确定性投影；
6. 让前端编辑器和后端校验器共同使用同一个模型。

这是最重要的一步。

### 第二阶段：将现有能力封装成工具

把现有 FastAPI 能力封装为 MCP 或标准 API：

- 文档解析工具；
- LightRAG 检索工具；
- 三元组抽取工具；
- 图谱写入工具；
- 故障树生成工具；
- 规则校验工具；
- 证据查询工具；
- 人工审核提交工具。

### 第三阶段：用 Nexent 编排多 Agent

先实现最小工作流：

```text
用户输入顶事件
  ↓
检索 Agent
  ↓
抽取 Agent
  ↓
校验 Agent
  ↓
故障树生成 Agent
  ↓
规则校验
  ↓
专家确认
```

第二阶段再增加：

- 长文本分块 Agent；
- 多模型交叉评审；
- 低置信度自动返工；
- 冲突分析 Agent；
- 评估 Agent。

### 第四阶段：建立评测集

从论文、设备手册和人工修订记录中整理评测集，至少包含：

- 标准事件节点；
- 标准因果边；
- 标准层级；
- 标准 AND/OR 门；
- 原文证据；
- 人工审核结果。

建议评价以下指标：

- 事件 Precision/Recall/F1；
- 关系方向准确率；
- 证据覆盖率；
- 层级准确率；
- AND/OR 门准确率；
- 故障树结构相似度；
- 专家采纳率；
- 单任务平均 LLM 成本；
- 长文档成功率。

## 十三、最终建议

当前最合适的路线是：

> **选择 Nexent 作为 Agent 协作和重构平台，保留 LightRAG 作为检索与知识处理核心；通过统一数据模型、证据溯源、确定性投影和可量化评估，解决长文本抽取、模型不互通和 AI 专家辅助三个核心问题。**

理由是：

1. 更适合现有开源、自主部署和代码级改造需求；
2. **可以补上多 Agent、A2A、Skill、MCP、记忆和评估能力；**
3. **可以把“抽取—校验—修复—人工审核”变成可执行的工作流；**
4. 与现有 Docker、FastAPI、React、向量检索和图谱架构兼容；

需要特别注意：

> **Nexent 解决的是 Agent 工程和协作问题，不能自动解决故障树领域建模问题。真正的核心仍然是统一数据模型、证据溯源、确定性投影和可量化评估。**

## 十四、项目结构审查补充结论

### 1. 当前结构问题

项目目前处于目录迁移未收口状态：旧的 `LightRAG/`、`fault-tree-ui/` 正在删除，新的 `backend/`、`frontend/` 尚未完成正式归档。前端同时存在 React 主界面、内嵌 Vue 编辑器和独立 `frontend-vue/` 原型，存在重复代码和失效接口。

此外，故障树的因果方向依赖图谱恢复时推断，AND/OR 门仍混在文本字段中，三元组、故障树和校验器的数据结构也没有完全统一。

### 2. 保留、重构与删除

**保留：**

- LightRAG 文档处理、检索、向量库和知识图谱核心；
- FastAPI 服务、规则校验器、React 管理界面和 Vue 编辑交互；
- Docker 部署思路和现有测试用例。

**重构：**

- 统一 `FaultEvent`、`FaultRelation`、`FaultTreeDraft` 数据模型；
- 将因果方向、`gate_type`（AND/OR）、证据和置信度改为结构化字段；
- 让顶事件成为用户明确输入；
- 统一生成、编辑、校验的 API 和数据格式；
- 生成结果由后端保存为 draft，前端通过 `draft_id` 获取和提交修改；
- 统一依赖、启动入口和构建方式。

**删除或归档：**

- 独立的 `frontend-vue/` 原型；
- 不存在后端实现的前端 API；
- `config.py.bak`、`test001.json` 等备份和测试产物；
- 根目录空入口、旧锁文件和过时路径引用。

### 3. 与 Nexent 的衔接方式

Nexent 不替代 LightRAG，也不直接操作底层图数据库。建议由 Nexent 负责 Agent 编排，LightRAG 和故障树领域服务负责实际处理：

```text
Nexent Agent
  → 检索 / 抽取 / 校验 / 修复 / 审核
  → 稳定的 HTTP API 或 MCP 工具
  → LightRAG + 故障树领域服务
```

推荐顺序：

1. 收口仓库和前端；
2. 统一领域模型与 API；
3. 修复方向、门类型和证据链；
4. 将现有能力封装为 API/MCP 工具；
5. 最后用 Nexent 编排多 Agent 工作流。
